# NuGet package naming and versioning

The pluggable image-processing abstraction (Core + SkiaSharp + ImageFlow processors) is going public on nuget.org, so package identity needed to be locked before any CI/publish tooling is built.

**Naming**: `Krebil.Umbraco.Image.Processing.Core`, `.SkiaSharp`, `.ImageFlow`, and `.UmbracoExtensions` (see ADR-0006) — the `Krebil.` prefix matches the author's existing published package (`Krebil.UmbracoAzureSearch`), and the rest is the existing project/assembly name unchanged, so `PackageId` needs no divergence from `AssemblyName`. `Umbraco.Image.Processing.Service`, the `Umbraco` sample, and `Umbraco.Image.Processing.AppHost` stay unpublished — they're apps, not libraries.

**Versioning**: lockstep. All four packages always ship the same version number on every release, even if only one changed, mirroring the actual `Umbraco.Cms.*` packages this abstraction positions itself as a drop-in replacement for. Considered independent per-package semver with an explicit compatible-range dependency on Core, but rejected: it adds a real maintenance burden (reasoning about which packages need a bump on every change, consumers ending up with mismatched Core/processor versions) that lockstep avoids entirely, at the cost of occasionally publishing a version bump for a package with no functional change.

**Release mechanism**: tag-triggered publish, not an automated version-bump bot. A single `<Version>` lives in `Directory.Build.props`, shared by all three package projects. Bumping it is a manual commit; pushing a matching git tag (e.g. `v1.2.0`) runs a GitHub Actions workflow that builds, runs the full test suite (including the parity suite from ADR-0003), packs all three packages, and publishes to nuget.org only on green. Ordinary branch/PR pushes run a separate build+test-only workflow with no publish step. Considered an automated bot (Release Please / Nerdbank.GitVersioning-style) that bumps version and publishes from conventional-commit history; rejected as tooling overhead that pays off with multiple contributors driving commit conventions, not a solo maintainer — an explicit human decision point for "is this actually a release" is preferable here anyway, since a shared version means every publish touches all three packages regardless of which one changed.
