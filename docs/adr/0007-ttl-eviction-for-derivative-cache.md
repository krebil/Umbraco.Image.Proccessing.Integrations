# Derivative cache eviction is TTL, not LRU/max-size

`IDerivativeImageCache` and `LocalDiskDerivativeImageCache` have no eviction at all today — every unique derivative persists forever, a real gap against stock `Umbraco.Cms.Imaging.ImageSharp`'s cache-management behavior, and a growth problem once Blob storage (ADR-0006 area) ships.

Decided: v1 adds TTL-based eviction to `IDerivativeImageCache`, implemented for both the local-disk and Blob backends, driven by the existing `ImageProcessingOptions.CacheControlMaxAge` (default 365 days — already present, matching Umbraco's own `Cache:CacheMaxAge` semantics exactly, but currently unused by anything). No new setting needed. Deliberately not LRU or max-size: `ImageProcessingUrlGenerator` already writes a `v` query parameter from `options.CacheBusterValue` into every generated URL, so the cache key already changes whenever the source image does — a derivative cached under a stale `v` is never requested again by any live URL, it's just dead weight. Correctness therefore never depends on eviction timing; TTL only needs to reclaim space from entries no longer referenced by any current URL, which is a simpler policy than LRU/max-size and doesn't require tracking access recency or total cache size.
