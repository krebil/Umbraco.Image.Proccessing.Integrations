# Umbraco-specific interface adapters split into their own package

Core currently carries a hard `PackageReference` on `Umbraco.Cms.Core`, solely because it implements Umbraco's own `IImageUrlGenerator`/`IImageDimensionExtractor` interfaces for in-process mode. The standalone deployment mode has no Umbraco involvement at all, yet the `Service` reference implementation still pulls in `Umbraco.Cms.Core` transitively through Core — every consumer inherits an Umbraco dependency (and the version-range constraints of ADR-0005) regardless of whether they run in-process or standalone.

Decided: split the two Umbraco-interface implementations out of Core into a fourth package, `Krebil.Umbraco.Image.Processing.UmbracoExtensions`. Core becomes fully Umbraco-agnostic (command model, `IImageProcessor` seam, HMAC signing, storage abstraction, no `Umbraco.Cms.Core` reference at all); in-process consumers add `UmbracoExtensions` on top, standalone consumers never touch it. This reopens ADR-0001's "three packages" naming/lockstep decision to four, versioned and named the same way.

Considered keeping the hard dependency on one Core package (simpler, matches the code as built, and in-process is the primary/more common use case so most consumers need both pieces anyway). Rejected: standalone is an explicit, load-bearing use case for this project (not a hypothetical), and a package that claims to be usable "standalone or in Umbraco" shouldn't force every standalone consumer to carry an unused CMS dependency and its version-compatibility surface just because the majority use case happens to need it.
