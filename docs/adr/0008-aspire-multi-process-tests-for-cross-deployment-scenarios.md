# Aspire-orchestrated multi-process tests for genuine cross-deployment scenarios

This repo already has two shapes of integration test. `WebApplicationFactory`-based tests (ticket 07's `MediaResolutionTests`) host an app in-process via `TestServer` — fast, but everything runs in one process, one AppDomain, one config resolution. Aspire-driven tests (ticket 05's `AzureBlob.TestHost` + `DistributedApplicationTestingBuilder`) boot a real dependency as its own process and talk to it over a real network endpoint.

Ticket 11 (Blob-backed original image source + real media-resolution E2E tests) needed to pick between these for testing that Umbraco and the standalone Service correctly resolve a real, Umbraco-saved image. `WebApplicationFactory` can prove DI wiring and middleware ordering inside one app, but it cannot exercise behavior that only exists *because* Umbraco and the Service are separate deployments: the real HTTP redirect a browser would actually follow, each side resolving its own independently-configured settings, or — central to ticket 12's HTTP-proxy original image source — a redirect loop that only manifests when the Service's own outbound request round-trips back to Umbraco over the network.

**Decided:** any integration test whose point is to prove correct behavior *across* the Umbraco/Service deployment boundary must boot both as genuinely separate processes communicating over real HTTP, via Aspire's `DistributedApplicationTestingBuilder` against the real `Umbraco.Image.Processing.AppHost` project graph — or a dedicated test AppHost when the real one drags in unrelated slow/flaky dependencies, mirroring `AzureBlob.TestHost`'s reasoning from ticket 05. `WebApplicationFactory`/`TestServer` stays the right tool when a test is scoped to one app's own middleware pipeline or DI wiring and there's no cross-deployment behavior to prove (ticket 07's existing tests, most unit-level middleware tests) — it's cheaper and shouldn't be replaced just for uniformity.

This applies directly to ticket 12: a redirect-loop regression test for the HTTP-proxy original image source is only meaningful against two real, separately-listening processes — a same-process `TestServer` call wouldn't exercise the real network round trip the loop depends on.
