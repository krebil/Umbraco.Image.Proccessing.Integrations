# 10 — CI: tag-triggered publish workflow

**What to build:** A maintainer publishes a release by pushing a `v*` git tag against a version already committed to `Directory.Build.props` — a deliberate, auditable action, not automatic on every merge. The workflow builds, runs the full test suite (reusing ticket 09's gate), packs all four `Krebil.*` packages, and pushes to nuget.org only when everything is green.

**Blocked by:** 02 (packaging identity/licensing must be correct before anything is packed), 09 (reuses its build+test gate).

## Comments

- **Five packages, not four — scope decision, not a ticket deviation**: the ticket text and `CONTEXT.md` both say "four" product packages, but `Umbraco.Image.Processing.AzureBlob` was already given full packaging identity in ticket 05 (`PackageId = Krebil.Umbraco.Image.Processing.AzureBlob`, `PackageLicenseExpression = MIT`) — pack-ready exactly like the other four, just never wired into a publish pipeline or documented as part of "the product." The user explicitly decided to include it as a fifth published package in this workflow, so `publish.yml` packs and pushes all five. **Flag for follow-up**: `CONTEXT.md` line 8 ("The four published NuGet packages...") is now stale and should be updated to five once this workflow lands; `Directory.Build.props`'s own comment ("Core, SkiaSharp, ImageFlow, and UmbracoExtensions are versioned in lockstep") is also stale in the same way, though it's still technically true that AzureBlob shares the same `<Version>` value even without being named. Neither doc was edited as part of this ticket — flagging only, per instruction.
- **Gate reuse — `workflow_call`, not copy-pasted steps**: ticket 09's own resolution comments considered and deliberately skipped a `workflow_call` reusable-workflow abstraction, reasoning that ticket 10's pack/push steps would need to run after tests in the same job/run, and a second job would add artifact-passing complexity. That concern doesn't actually apply here: `dotnet pack` does its own full build, so `pack-and-publish` never needs `test`'s build output — it just needs to *know `test` passed*, which `needs:` alone provides. So `build-and-test.yml` gained a `workflow_call:` trigger (alongside its existing `pull_request`/`push`), and `publish.yml`'s first job is `test: uses: ./.github/workflows/build-and-test.yml`. This is genuine step reuse — one place the restore/build/test sequence is written, referenced from both workflows — not a duplicate copy that could silently drift. Each file's header comment cross-references the other.
- **`pack-and-publish` job**: `needs: test`, so it never starts unless the full reused test suite passed. Steps: checkout, `actions/setup-dotnet@v4` pinned to `10.0.x` (matching `build-and-test.yml`), one `dotnet restore` on the `.sln`, then five `dotnet pack <csproj> --no-restore -c Release -o ./nupkgs` steps (one per packable project, named steps for per-package pass/fail visibility in the Actions UI, matching ticket 09's per-project-step precedent), then one `dotnet nuget push "./nupkgs/*.nupkg" --source https://api.nuget.org/v3/index.json --api-key "${{ secrets.NUGET_API_KEY }}" --skip-duplicate` step. No `continue-on-error` anywhere in either job — verified by grepping both workflow files; the only match is this explanatory comment itself. Standard GitHub Actions step-ordering and `needs:` job-ordering means any restore/pack/push failure stops the pipeline before a later push could run.
- **`--skip-duplicate`**: makes a workflow re-run (e.g. retrying a run that failed partway, or re-running after a version was already published) safe — a duplicate-version push is skipped rather than erroring, so it doesn't block sibling packages in the same run.

- **No real publish performed**: no `v*` tag was pushed, no GitHub Actions run was triggered, and nothing was pushed to the real `https://api.nuget.org/v3/index.json`. `git status` shows only the two workflow files changed (`.github/workflows/build-and-test.yml` modified, `.github/workflows/publish.yml` new) — all local pack/push verification happened against `/tmp` paths, cleaned up afterward, and the repo's committed `.gitignore` already excludes `bin`/`obj`, so the local `Release`-configuration build artifacts from packing don't show up as changes either.
- **Manual prerequisite — cannot be completed by this ticket**: `publish.yml` reads `secrets.NUGET_API_KEY`. Nothing in this repo or this workflow can create that secret. Before a real `v*` tag push can ever succeed, the repo owner must manually add a `NUGET_API_KEY` secret under GitHub repo Settings > Secrets and variables > Actions (or on a protected Environment, if this job is later scoped to one). Without it, `test` and all five `pack` steps will still succeed on a real tag push, but the final `dotnet nuget push` step will fail with an authentication error. This is called out in `publish.yml`'s own header comment as well, so it's visible to anyone reading the workflow, not just this ticket file.
