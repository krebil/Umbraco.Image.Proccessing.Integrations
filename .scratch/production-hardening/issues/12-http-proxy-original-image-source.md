# 12 — HTTP-proxy original image source for separate-deployment disk mode

**What to build:** A third `IOriginalImageSource` implementation for the case ticket 11's Blob source doesn't cover: Umbraco's media stays on plain local disk, but Umbraco and the standalone Service are genuinely separate deployments with no shared volume. `LocalDiskOriginalImageSource` requires a shared filesystem (see ticket 11's comments); `AzureBlobOriginalImageSource` requires Blob-backed media. Neither applies here — the Service has to fetch the original from Umbraco itself over HTTP.

**Blocked by:** none functionally, but hold off starting implementation until 11 lands — both touch `src/Umbraco/Program.cs` and `Umbraco.Image.Processing.AppHost/AppHost.cs`, and running two agents on those files concurrently risks conflicting edits.

**Status:** open

- [ ] New `ProxyOriginalImageSource : IOriginalImageSource` (working name — reconsider against `HttpOriginalImageSource` for consistency with naming-by-mechanism, `LocalDiskOriginalImageSource`/`AzureBlobOriginalImageSource` name by *where*, not *how*; pick whichever reads clearer once written) in `Core` or a new small package — decide which; it has no Umbraco-specific or Blob-specific dependency, so `Core` is the natural home unless there's a reason to keep it out
- [ ] Resolve the redirect-loop problem first, as a design step before writing the fetch logic: Umbraco's Standalone-mode redirect middleware (`Program.cs:71-94`) redirects any request under `RoutePrefix` with a supported extension, unconditionally — a naive `GET {umbracoBaseUrl}{requestPath}` from the Service would bounce straight back to the Service and loop.
  - Rejected: gating on "no query string present" — plain pass-through browser requests (unprocessed `<img src>` links) also carry no query string and must still be redirected, so this signal can't distinguish "browser wants a redirect" from "Service wants the raw file." Confirmed via the existing pass-through path in `ImageProcessingMiddleware.cs:72-76`, which handles no-query-string requests as a normal case, not a special one.
  - **Chosen approach**: expose the raw-original fetch under a path that doesn't nest under `RoutePrefix` at all (e.g. `/__image-origin/{**path}`), mapped straight to Umbraco's media file system. Because the redirect middleware only matches on `path.StartsWithSegments(RoutePrefix)`, this request never enters its matching logic — no bypass branch needed in existing code, no risk of an exemption accidentally also matching real browser traffic.
  - Guard that endpoint with the existing `IHmacSigner`/`HmacSecretKey` (already shared via config between `Umbraco` and `Service`, already registered in Umbraco's DI since `AddImageProcessing()` runs unconditionally) rather than a new secret — the Service signs its own outbound request the same way it validates inbound ones. Route and signature are independent layers: the route avoids the loop, the signature stops the new endpoint being an unauthenticated bulk-download of every original.
- [ ] Config: the Service needs Umbraco's internal base URL to call back to (likely a new `ImageProcessing:Proxy:UmbracoBaseUrl`-shaped setting, separate from `Standalone:BaseUrl` which points the other direction)
- [ ] DI extension on `IImageProcessingBuilder`, `Replace` pattern matching tickets 05/11
- [ ] Contract-level tests: found → stream returned; not found on Umbraco's side → null (middleware falls through, same contract as the other two sources); redirect-loop regression test (a request through this source must not come back through Umbraco's redirect middleware) — per ADR-0008, this test must boot Umbraco and the Service as genuinely separate processes (Aspire `DistributedApplicationTestingBuilder`), not `WebApplicationFactory`/`TestServer` — a same-process test wouldn't exercise the real network round trip the loop depends on
- [ ] `AppHost` wiring for local dev: needs Umbraco's internal endpoint reachable from the Service in the same way `Standalone:BaseUrl` already flows the other direction
