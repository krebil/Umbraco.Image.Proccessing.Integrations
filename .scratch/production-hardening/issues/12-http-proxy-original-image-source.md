# 12 — HTTP-proxy original image source for separate-deployment disk mode

**What to build:** A third `IOriginalImageSource` implementation for the case ticket 11's Blob source doesn't cover: Umbraco's media stays on plain local disk, but Umbraco and the standalone Service are genuinely separate deployments with no shared volume. `LocalDiskOriginalImageSource` requires a shared filesystem (see ticket 11's comments); `AzureBlobOriginalImageSource` requires Blob-backed media. Neither applies here — the Service has to fetch the original from Umbraco itself over HTTP.

**Blocked by:** none functionally, but hold off starting implementation until 11 lands — both touch `src/Umbraco/Program.cs` and `Umbraco.Image.Processing.AppHost/AppHost.cs`, and running two agents on those files concurrently risks conflicting edits.

**Status:** resolved

- [x] New `HttpOriginalImageSource : IOriginalImageSource` (chosen over `ProxyOriginalImageSource` — see resolution notes) in `Core`; confirmed it has no Umbraco-specific or Blob-specific dependency
- [x] Resolve the redirect-loop problem first, as a design step before writing the fetch logic: Umbraco's Standalone-mode redirect middleware (`Program.cs:71-94`) redirects any request under `RoutePrefix` with a supported extension, unconditionally — a naive `GET {umbracoBaseUrl}{requestPath}` from the Service would bounce straight back to the Service and loop.
  - Rejected: gating on "no query string present" — plain pass-through browser requests (unprocessed `<img src>` links) also carry no query string and must still be redirected, so this signal can't distinguish "browser wants a redirect" from "Service wants the raw file." Confirmed via the existing pass-through path in `ImageProcessingMiddleware.cs:72-76`, which handles no-query-string requests as a normal case, not a special one.
  - **Chosen approach**: expose the raw-original fetch under a path that doesn't nest under `RoutePrefix` at all (`/__image-origin/{**path}`, `HttpOriginalImageSource.OriginRoutePrefix`), mapped straight to Umbraco's media file system. Because the redirect middleware only matches on `path.StartsWithSegments(RoutePrefix)`, this request never enters its matching logic — no bypass branch needed in existing code, no risk of an exemption accidentally also matching real browser traffic. Proven directly by the E2E redirect-loop test, not just inferred.
  - Guard that endpoint with the existing `IHmacSigner`/`HmacSecretKey` (already shared via config between `Umbraco` and `Service`, already registered in Umbraco's DI since `AddImageProcessing()` runs unconditionally) rather than a new secret — the Service signs its own outbound request the same way it validates inbound ones. Route and signature are independent layers: the route avoids the loop, the signature stops the new endpoint being an unauthenticated bulk-download of every original.
- [x] Config: the Service needs Umbraco's internal base URL to call back to — `ImageProcessing:Proxy:UmbracoBaseUrl` (`HttpOriginalImageSourceOptions.UmbracoBaseUrl`), separate from `Standalone:BaseUrl` which points the other direction
- [x] DI extension on `IImageProcessingBuilder`, `Replace`-equivalent pattern matching tickets 05/11 (see resolution notes on why it isn't a literal `Replace(...)` call)
- [x] Contract-level tests: found → stream returned; not found on Umbraco's side → null (middleware falls through, same contract as the other two sources); redirect-loop regression test (a request through this source must not come back through Umbraco's redirect middleware) — booted via Aspire `DistributedApplicationTestingBuilder` against the real product `AppHost`, per ADR-0008
- [x] `AppHost` wiring for local dev: Umbraco's internal endpoint is reachable from the Service in the same way `Standalone:BaseUrl` already flows the other direction

This ticket is the remaining gap for teams who deploy separately but don't use Blob media.

## Implementation notes (resolution)

- **Naming — `HttpOriginalImageSource`, not `ProxyOriginalImageSource`**: the ticket flagged the naming tension directly (`LocalDisk`/`AzureBlob` name by *where*, this one has no "where"). Settled on naming by mechanism, since that's what actually varies here — matched through the DI method too: `UseHttpOriginalImageSource`, not the ticket's own working suggestion `UseHttpProxyOriginalImageSource`, for exact symmetry with `UseAzureBlobOriginalImageSource` (method name = class name in both existing cases). Worth a reviewer's second look since it's a naming call, not a functional one.
- **`HttpOriginalImageSource`** (`Storage/HttpOriginalImageSource.cs`, Core): builds `{UmbracoBaseUrl}{OriginRoutePrefix}{relativePath}`, signs it with the same `IHmacSigner` injected into the class (not a second instance/secret), and treats *any* non-success status — 404 (genuinely missing) and 400 (bad/missing HMAC token) alike — as `null`, matching the same "fall through" contract `ImageProcessingMiddleware` already relies on for the other two sources. Buffers the response into a `MemoryStream` rather than returning `HttpContent`'s own stream, for the same reason `AzureBlobOriginalImageSource` buffers: the interface contract needs a seekable stream (the middleware reads image headers, then rewinds to reprocess), and neither an HTTP response stream nor Blob's own download stream is seekable.
- **`OriginRoutePrefix` is a `public const string` on `HttpOriginalImageSource` itself** (`/__image-origin`), not a configurable option: both sides — this class building requests, and Umbraco's own endpoint mapping matching them — have to agree on it, and there's no real scenario where either side would need to move it independently of the other. Umbraco's endpoint file references it directly (`HttpOriginalImageSource.OriginRoutePrefix`) rather than duplicating the literal string.
- **DI registration deviates from a literal `Replace(...)` call, functionally not in spirit**: `UseHttpOriginalImageSource` needs a typed `HttpClient`, so it uses `AddHttpClient<IOriginalImageSource, HttpOriginalImageSource>()` — but that method does its own `Add` (not `TryAdd`) internally and doesn't hand back a plain `ServiceDescriptor` the way `Replace(...)` needs. Spelled out instead as `Services.RemoveAll<IOriginalImageSource>()` immediately before the `AddHttpClient` call — exactly what `Replace` does internally, just visible as two steps because the typed-client API doesn't compose with it directly.
- **`Microsoft.Extensions.Http`/`AddHttpClient` needs no new package reference in Core**: confirmed by building Core in isolation before writing any DI code — `Microsoft.Extensions.Http.dll` ships inside the `Microsoft.AspNetCore.App` shared framework Core already references via `FrameworkReference`, so ADR-0001's "dependency-free Core" framing holds; no `PackageReference` was added anywhere in Core.
- **Umbraco-side endpoint — `src/Umbraco/OriginImageEndpoints.cs`, not a packaged `UmbracoExtensions` method**: mirrors `E2ETestSupportEndpoints.cs`'s shape (a `MapXEndpoints(this WebApplication app)` extension in the sample app) per the ticket's own steer, but explicitly documented as production code, not test support. This matches the existing precedent set by the Standalone-mode redirect middleware, which is also hand-rolled directly in the sample's `Program.cs` rather than packaged — the quickstart doc teaches both as glue code a consumer copies into their own `Program.cs`, not as calls into a provided API. Mounted **unconditionally** (not gated on `ImageProcessing:Mode`): it's only ever hit when the Service is separately configured with `Storage:Mode=HttpProxy`, but costs nothing to register otherwise (no new unauthenticated surface — same HMAC guard as every other image request) and avoids a branch here that would need to track a config value living entirely on the Service's side, invisible to this app.
- **A real, verified-not-assumed bug found and fixed in `AppHost.cs` while building the redirect-loop test**: the E2E harness (`UmbracoServiceGraphHarness.StartAsync`) has always passed `--ImageProcessing:Mode=Standalone` to the AppHost, and its own doc comment claims this "always runs Umbraco in Standalone image-processing mode." It didn't — `AppHost.cs` never forwarded that AppHost-level config value onto Umbraco's own process env vars (unlike `Storage:Mode`, which *is* explicitly forwarded), so Umbraco silently stayed on its `appsettings.json` default (`InProcess`) regardless. This went uncaught by ticket 11's two existing E2E tests because neither ever exercises Umbraco's own redirect middleware — both issue requests straight against the Service. Ticket 12's redirect-loop test is the first one that actually needs Standalone mode to be genuinely active (it asserts a real 302 from Umbraco), so it would have failed immediately without this fix. Fixed by forwarding `builder.Configuration.GetValue("ImageProcessing:Mode", "InProcess")` onto `umbraco.WithEnvironment("ImageProcessing__Mode", ...)`, mirroring the existing `Storage:Mode` forwarding pattern. Re-ran ticket 11's own two E2E tests after this fix — both still pass; neither was relying on Umbraco staying in InProcess mode.
- **`Storage:Mode=HttpProxy` in `AppHost.cs` only touches the Service, not Umbraco**: unlike the `AzureBlob` branch (which sets `ImageProcessing__Storage__Mode=AzureBlob` on *both* apps, because both genuinely need Blob-flavored behavior), `HttpProxy` only changes how the *Service* resolves originals — Umbraco's own media storage stays plain local disk, so Umbraco gets no `Storage:Mode` env var at all in this branch and keeps its own default. The two apps' `ImageStorageMode` enums (`src/Umbraco/Program.cs` and the Service's own `Program.cs`) are separate types that happen to share a config key and, coincidentally, a value in the Blob case only — `HttpProxy` doesn't exist as a member on Umbraco's own enum at all, deliberately, since it has no meaning there.
- **`ImageProcessing__Proxy__UmbracoBaseUrl` wired unconditionally, not gated**: mirrors `ImageProcessing__Standalone__BaseUrl`'s existing unconditional wiring in the opposite direction — cheap to set, harmless when `Storage:Mode` stays at its `LocalDisk` default. Deliberately **not** paired with a `.WaitFor(umbraco)` on the Service: `umbraco` already `.WaitFor(imageProcessingService)`, so adding the reverse would deadlock startup (each side waiting on the other). Not needed anyway — Aspire endpoint references resolve to an address as soon as the port is allocated, independent of whether the referenced process has actually started listening yet.
- **Contract tests** (`Umbraco.Image.Processing.Core.Tests/Storage/HttpOriginalImageSourceTests.cs`): a minimal in-process `Microsoft.AspNetCore.TestHost.TestServer` stands in for Umbraco's endpoint, validating the same HMAC token the real endpoint would and serving known bytes for one known path. Three tests: found → correct bytes, missing path → `null`, **wrong HMAC secret key → `null`** (added beyond the ticket's literal ask, since the HMAC guard is central to this ticket's whole security design and is cheap to cover directly rather than trust by inspection alone). Needed one new test-only package reference, `Microsoft.AspNetCore.TestHost` (10.0.0) — Core.Tests only, not Core itself.
- **Redirect-loop E2E test** (`Umbraco.Image.Processing.E2E.Tests/HttpProxyOriginalImageSourceEndToEndTests.cs`): extends `UmbracoServiceGraphHarness` with `storageMode: "HttpProxy"` support (no harness code changes needed beyond a new `SignedOriginUrl` helper — the existing `StartAsync(storageMode)` parameter already forwarded arbitrary strings straight to `AppHost.cs`'s own switch) and a `SignedOriginUrl` method that signs a request the same way `HttpOriginalImageSource` itself would, for issuing directly against Umbraco without going through the Service. The test asserts three things, not just the end-to-end resize: (1) a plain pass-through request to Umbraco's own `/media/...` genuinely 302s — a sanity check that Standalone mode is actually active, using a `HttpClientHandler { AllowAutoRedirect = false }` so the redirect is observable instead of silently followed; (2) the raw-origin route itself returns 200 directly, not a redirect, when hit straight against Umbraco; (3) a full resize request against the Service succeeds end-to-end. Reuses the same best-effort `wwwroot/media` cleanup pattern ticket 11's `MediaResolutionEndToEndTests` uses for its LocalDisk test, since HttpProxy mode also writes into the real checked-in media folder.
- **`docs/quickstart-standalone.md`**: added a third mode section alongside LocalDisk/Blob, showing the origin-endpoint snippet as glue code to copy (matching how the redirect-middleware section is already presented), not a call to a packaged method — consistent with where the actual implementation lives (the sample app, not a NuGet package).
- Full solution build: 0 warnings/errors. All 7 test projects green: Core **71** (68 + **3 new**), SkiaSharp 17, ImageFlow 19, UmbracoExtensions 10, AzureBlob 12, Service.Tests 2 (unchanged), E2E.Tests **3** (2 + **1 new**) — **134 total**, up from ticket 11's 130.
