# 11 — Blob-backed original image source + real end-to-end media-resolution tests

**What to build:** Two related gaps found while auditing test coverage for media resolution:

1. A new `AzureBlobOriginalImageSource : IOriginalImageSource` in `Krebil.Umbraco.Image.Processing.AzureBlob`, reading original (unprocessed) images directly from Azure Blob Storage. This is a different seam from `AzureBlobDerivativeImageCache` (ticket 05) — that class caches already-processed crops; this one resolves the raw source those crops are made from. Today only `LocalDiskOriginalImageSource` exists, so the standalone Service cannot resolve originals at all when Umbraco's media is Blob-backed instead of local disk.
2. Real end-to-end tests proving an image actually saved through Umbraco's media pipeline is resolvable through the standalone Service — for both local-disk mode (today's default) and Blob mode (once part 1 exists). The existing `MediaResolutionTests` (ticket 07) only *simulates* Umbraco's on-disk file layout by writing bytes to a temp folder computed via `UniqueMediaPathScheme` directly; it never starts a real Umbraco host or performs a real upload, so it doesn't actually prove the two independently-configured sides (Umbraco's media file system, the Service's `OriginalsRootPath`/Blob config) agree in a real deployment shape.

**Blocked by:** 05 (reuses the `AzureBlob` project, `AzuriteFixture`/`AzureBlob.TestHost` Aspire test infra). Extends 07's scope (real E2E coverage where 07 left a simulated stand-in).

**Status:** resolved

- [x] `AzureBlobOriginalImageSource` implements `IOriginalImageSource.OpenReadAsync`, reading the blob at the request's relative path from a configured container — parallel to `LocalDiskOriginalImageSource`'s root+relative-path resolution, no interface change needed
- [x] DI extension on `IImageProcessingBuilder` to register it (mirrors `UseAzureBlobDerivativeCache`'s `Replace` pattern from ticket 05)
- [x] `Umbraco` sample project references `Umbraco.StorageProviders.AzureBlob` and wires `.AddAzureBlobMediaFileSystem()`, so media can actually be stored in Blob when configured for that mode (currently the sample has no Blob media package at all — local disk is its only option)
- [x] `AppHost.cs` gives the `umbraco` project a `WithReference(blobs)`, matching what `image-processing-service` already gets, so both sides can share one Azurite-backed container in dev
- [x] New end-to-end test: boots the real `Umbraco` + `Service` project graph (Aspire `DistributedApplicationTestingBuilder`, against the real product `AppHost` — see steering note below on why not a stand-in host), saves an image through Umbraco's actual media pipeline (not a hand-written temp file), then resolves it through the standalone Service over HTTP — local-disk mode
- [x] Same end-to-end test shape for Blob mode: Umbraco configured with the Blob media file system (Azurite), Service configured with `AzureBlobOriginalImageSource` pointed at the same container, asserting resolution succeeds with no HTTP call back to Umbraco
- [x] Decide and record whether `MediaResolutionTests` (ticket 07) is superseded by the new real E2E test or kept alongside as a cheaper, host-less complement — **kept alongside**, see below

## Comments

- **Reference packages, confirmed with the user**: `Umbraco.StorageProviders.AzureBlob` is the package to add to the `Umbraco` sample for Blob-backed media storage (`dotnet add package`, wired via `.AddAzureBlobMediaFileSystem()` on the `CreateUmbracoBuilder()` chain, configured under `Umbraco:Storage:AzureBlob:Media`). `Umbraco.StorageProviders.AzureBlob.ImageSharp` is a reference for *how* to talk to the container correctly (its `AzureBlobFileSystemImageCache`-shaped read path) — not a dependency to take. Storage layout convention from that package family: a `/media` folder shaped by `IMediaPathScheme`, a `/cache` folder for its own ImageSharp cache (irrelevant here — this repo has its own cache seam, ticket 04/05).
- **Why this isn't just "reuse `AzureBlobDerivativeImageCache`"**: flagged explicitly during triage — the derivative cache stores already-resized output keyed by request; the original-image source has to resolve the *unprocessed* source file Umbraco itself wrote, at a path Umbraco's own `IMediaPathScheme` computed. Different read pattern, different container/prefix, no shared implementation.
- **Redirect middleware is orthogonal to original resolution**: confirmed via code read (`src/Umbraco/Program.cs`) that the Standalone-mode redirect middleware is a client-side 302 based on route prefix + extension, not a proxy, and doesn't gate on query strings. Processed-image URLs never hit Umbraco's host at all (`ImageProcessingUrlGenerator` bakes `ExternalBaseUrl` in at render time); only plain/unprocessed media links generated by Umbraco's own URL provider land on Umbraco's host and get redirected. Either way, once a request reaches the Service, `ImageProcessingMiddleware` resolves the original via `IOriginalImageSource` directly — no HTTP call back to Umbraco, for either pass-through or processed requests. This ticket doesn't need to touch that middleware; it only needs the Blob-backed source it currently lacks.

## Implementation notes (resolution)

- **`AzureBlobOriginalImageSource`** (`Storage/AzureBlobOriginalImageSource.cs`): its own `AzureBlobOriginalImageSourceOptions` (`ConnectionString`, `ContainerName`, `BlobPathPrefix`), kept independent of `AzureBlobCacheOptions` since the two containers are different concerns even when pointed at the same storage account. Uses `BlobClient.DownloadContentAsync` (buffers into a real, seekable `MemoryStream` via `BinaryData.ToStream()`), not the streaming download `AzureBlobDerivativeImageCache` uses — the interface contract requires a genuinely seekable stream (the middleware reads image headers, then rewinds to re-read for processing), and Blob's streaming download is forward-only. Doesn't create its container (unlike the derivative cache): that container's lifecycle belongs to Umbraco's media file system, confirmed as the real-world convention (Azure Blob containers are provisioned via IaC ahead of deploy, not auto-created on first write).
- **`BlobPathPrefix` default, verified against the real package source, not assumed**: read `Umbraco.StorageProviders.AzureBlob`'s actual `AzureBlobFileSystem.GetBlobName` (via `gh api` against the `umbraco/Umbraco.StorageProviders` repo) rather than guessing. Confirmed: with `AzureBlobFileSystemOptions.ContainerRootPath` left unset (the common case), it defaults to the media file system's `VirtualPath`, itself defaulted from `GlobalSettings.UmbracoMediaPath` (`~/media`) — so a real deployment's blob names are `media/<UniqueMediaPathScheme path>`, not the bare relative path. `BlobPathPrefix` defaults to `"media"` to match. Getting this wrong would have been exactly the class of silent wiring bug this ticket exists to catch — it would have surfaced as the Blob-mode E2E test's `AzureBlobOriginalImageSource` reading against the wrong blob name and returning 404, not as an obvious startup failure.
- **Azurite container must be pre-created**: hit for real during the Blob-mode E2E test's first run — Umbraco's own media save failed with `Azure.RequestFailedException: ContainerNotFound` writing through `Umbraco.StorageProviders.AzureBlob`. That package (like real Azure) expects the container to already exist; it doesn't auto-create one (unlike `AzureBlobDerivativeImageCache`, which does). Fixed in `AppHost.cs` via Aspire's `AddBlobContainer(name, blobContainerName)` on the storage-account resource (not the obsolete overload on the blobs resource), which provisions the container against Azurite at startup — the dev/emulator equivalent of the IaC step a real deployment would need anyway.
- **E2E test architecture — steered mid-ticket to real multi-process orchestration**: the brief originally left discretion for a `WebApplicationFactory`-only fallback if full Aspire orchestration proved impractical. Before that fallback was needed, the user explicitly narrowed scope: the deliverable must be genuinely separate `Umbraco` and `Service` *processes* communicating over real HTTP, driven via `DistributedApplicationTestingBuilder` against the real product `Umbraco.Image.Processing.AppHost` — not a stand-in host (unlike ticket 05's `AzureBlob.TestHost`, which deliberately avoids the full graph; here the full graph *is* the thing under test, so using the real `AppHost` is right, not overkill). Built exactly that; no fallback was needed — both LocalDisk and AzureBlob E2E tests pass against the real multi-process graph on the first architecture attempted.
- **New project**: `src/Umbraco.Image.Processing.E2E.Tests`, referencing `AppHost` (for the generated `Projects.Umbraco_Image_Processing_AppHost` type-safe entry point Aspire's SDK produces for any referenced Aspire host project), Core, and UmbracoExtensions (for constructing signed URLs the same way `MediaResolutionTests` does). `UmbracoServiceGraphHarness` centralizes boot/readiness/signing so the two tests (LocalDisk, AzureBlob) share nothing but a `storageMode` string.
- **Real media save without driving backoffice OAuth**: proving genuine separate processes doesn't require the *save* to go through the backoffice's Management API login flow — only that Umbraco's own real media-saving code runs, in Umbraco's own process. Added `E2ETestSupportEndpoints.cs` (`POST /e2e-test-support/media`), calling the exact same public `ContentExtensions.SetValue(...)` → `MediaFileManager.StoreFile` → real `IMediaPathScheme` → real `IFileSystem` (local disk or Blob) path a real upload would. Driving the full OAuth flow purely to reach the same call would have added significant harness complexity for zero additional coverage of what's actually under test (media resolution, not backoffice auth).
- **Test isolation — database yes, media folder no**: added a generically useful (not test-only) override in `AppHost.cs` — an absent-by-default `ConnectionStrings:umbracoDbDSN` forward from the AppHost's own config onto the `umbraco` resource — so each E2E run boots against a fresh temp SQLite file instead of the developer's real local `App_Data` database (essential: reusing the real dev DB across test runs would be state corruption, not just untidiness). Deliberately did **not** attempt the equivalent isolation for Umbraco's own local-disk media root (would need a full isolated content-root/`wwwroot`, since `UmbracoMediaPath` resolves against `WebRootPath` and a partial override risks breaking backoffice static assets) — LocalDisk-mode runs write into the real, checked-in `src/Umbraco/wwwroot/media/`, same as manual local testing would. Mitigated, not solved: the LocalDisk test computes the physical folder its own upload landed in and deletes it in a best-effort `finally`. Verified clean after a full test run (`git status` shows no residue). AzureBlob-mode has no equivalent concern — Azurite is ephemeral per test run.
- **HMAC secret key duplication**: the harness hardcodes the same fixed dev HMAC key already committed in `src/Umbraco/appsettings.json`, matching the pattern `MediaResolutionTests` already uses (its own freshly-generated key, since that suite fully controls both sides via `WebApplicationFactory` config injection). Here the harness can't inject config into the real running app the same way, so it has to know the real app's actual configured key. Not a secret in any meaningful sense (committed reference-implementation dev value), but flagging the coupling: if `appsettings.json`'s key ever changes, `UmbracoServiceGraphHarness.HmacSecretKeyBase64` needs updating too.
- Full solution build: 0 warnings/errors. All test projects green: Core 68, SkiaSharp 17, ImageFlow 19, UmbracoExtensions 10, **AzureBlob 12** (7 existing + **5 new** for `AzureBlobOriginalImageSource`), Service.Tests 2 (unchanged — kept, not superseded, see below), **E2E.Tests 2 (new)** — 116 total, plus the 2 new E2E tests bringing the grand total to 118.
- **`MediaResolutionTests` (ticket 07) kept, not superseded**: the two suites check different things and cost very differently. `MediaResolutionTests` (~1s, no Docker) pins down the narrow "do these two independently-configured root paths agree" contract in isolation, with a clean negative control (`ImageAtWrongRelativePath_IsNotResolvable`) that's cheap to keep green on every run. The new E2E suite (~30–55s including two full Umbraco boots, needs Docker for Azurite even in LocalDisk mode since the AppHost always declares the storage resource) proves the whole real pipeline end to end, but is too costly to be the *only* signal for a path-agreement regression a contributor would want fast feedback on. Keeping both mirrors ticket 04→05's contract-suite-plus-backend-specific-tests shape: cheap unit-level coverage plus one expensive, authoritative real-world proof.
