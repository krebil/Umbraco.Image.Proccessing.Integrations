# 05 — Azure Blob derivative cache + Azurite dev/test infra

**What to build:** A platform engineer can run the standalone Service across multiple instances behind a load balancer, sharing one derivative cache in Azure Blob Storage. Add a new `IDerivativeImageCache` implementation backed by Azure Blob Storage — additive against the existing seam, including the TTL eviction behavior from ticket 04, no interface change required. Wire an Azurite resource into `Umbraco.Image.Processing.AppHost` via Aspire's `AddAzureStorage().RunAsEmulator()`, so the Blob backend is developed and tested against a real Blob-API-compatible emulator with no Azure subscription required. Extend the shared cache-contract suite from ticket 04 to run parameterized against this Blob implementation + Azurite.

**Blocked by:** 04 (extends its contract suite; needs the eviction member already defined on the interface).

**Status:** resolved

- [x] New Blob-backed `IDerivativeImageCache` implementation exists, implementing read/write/clear and TTL eviction
- [x] `Umbraco.Image.Processing.AppHost` wires in an Azurite resource via `AddAzureStorage().RunAsEmulator()`
- [x] The Blob cache implementation can be configured to run against the Azurite emulator locally (no real Azure subscription needed)
- [x] The shared `IDerivativeImageCache` contract suite from ticket 04 runs parameterized against the Blob implementation + Azurite, alongside the local-disk backend, without duplicating test logic
- [x] Contract suite passes against both backends

## Comments

- **Package structure**: the Blob cache is a new fifth package, `src/Umbraco.Image.Processing.AzureBlob` → `Krebil.Umbraco.Image.Processing.AzureBlob` (MIT), not folded into Core. Core stays dependency-free (`FrameworkReference` only); only consumers who opt into Blob caching pull in `Azure.Storage.Blobs`. This wasn't spelled out in ADR-0001's "four packages" framing, so it was confirmed with the user before building rather than assumed — a new ADR should be added recording the five-package structure before publish (not done as part of this ticket; flagging for whoever picks up the packaging/versioning follow-through).
- **`AzureBlobDerivativeImageCache`** (`Storage/AzureBlobDerivativeImageCache.cs`): implements the same three operations plus `EvictExpiredAsync` from ticket 04's interface. Age tracking rides each blob's own server-set `Last-Modified` timestamp (refreshed on every overwrite) compared against an injected `TimeProvider` — mirrors `LocalDiskDerivativeImageCache`'s `LastWriteTimeUtc` approach, no extra metadata needed. Cache keys are SHA-256-hashed to blob names, same as the local-disk path hashing. Container existence is ensured once via a `Lazy<Task<BlobContainerClient>>`, not on every call.
- **DI**: `UseAzureBlobDerivativeCache(Action<AzureBlobCacheOptions> configure)` on `IImageProcessingBuilder`, registered via `Replace` (not `TryAdd`) since `AddImageProcessing()` already registers the local-disk cache as the default — same pattern `UmbracoExtensions`'s `AddUmbracoImageProcessing()` uses for the URL generator/dimension extractor.
- **Aspire wiring** (`AppHost.cs`): `builder.AddAzureStorage("storage").RunAsEmulator().AddBlobs("blobs")`, referenced onto the Service project via `WithReference(blobs)`. Not force-enabled — local disk stays the Service's actual default cache backend; this only makes the connection available. Verified via a real `dotnet run`: all four resources (`umbraco`, `image-processing-service`, `storage`, `blobs`) reached `Running`/ready cleanly, then torn down.
- **Test infra — built with Aspire, not a standalone container library** (per explicit steer mid-ticket): initially wired the contract suite against Azurite via `Testcontainers.Azurite`; switched to Aspire's own hosting/testing APIs instead, so dev (`AppHost`) and test both drive Azurite through the same `AddAzureStorage().RunAsEmulator()` call rather than two different mechanisms. This needed a new minimal project, `Umbraco.Image.Processing.AzureBlob.TestHost` — a bare Aspire AppHost whose only resource is Azurite/blobs, `IsPackable=false`, never published — referenced from `AzureBlob.Tests` via `DistributedApplicationTestingBuilder.CreateAsync<Projects.Umbraco_Image_Processing_AzureBlob_TestHost>()`. Doing this against the real product `AppHost` directly was considered and rejected: it would start the full Umbraco+Service graph (slow, and drags in unrelated failure modes) just to get one storage resource. Both still ultimately run Azurite via Docker — Aspire orchestrates the same container underneath, it just replaces the bespoke Testcontainers dependency (which also happened to carry an unresolved `SSH.NET` high-severity advisory transitively; gone now that Testcontainers isn't referenced at all).
- **Azurite image pin**: the TestHost pins `mcr.microsoft.com/azure-storage/azurite:latest` — Testcontainers.Azurite's own default image tag (3.28.0) turned out to reject the `Azure.Storage.Blobs` SDK's current default API version (`2025-05-05`) with a hard 400. `latest` keeps the emulator's supported API surface current instead of pinning a version-compatibility problem in place; this concern doesn't apply to real Azure, which always supports current API versions.
- **A real bug found and fixed, not in the Blob cache — in ticket 04's shared contract suite itself**: `TryOpenReadAsync_EntryOlderThanMaxAge_ReturnsNull` and `EvictExpiredAsync_PhysicallyRemovesExpiredEntries` pushed the fake clock only 1 second past `maxAge`. That's fine for local disk (the timestamp is written by the test's own process, synchronously) but not for Blob: its timestamp comes from Azurite's own real server clock, and real wall-clock time (container/connection setup, network round-trip) elapses between constructing the frozen `FakeTimeProvider` baseline and the blob's actual `Last-Modified` being recorded — confirmed empirically (observed ~3s of real elapsed time eating the 1s margin, verified via a throwaway diagnostic test before touching any real code, not guessed). Fixed by widening the boundary margin to 2 minutes (`BoundaryMargin`, cost-free since `Advance()` is virtual/instant) in `DerivativeImageCacheContractTests.cs`. This is now documented in the suite as a general property any real-external-clock backend needs from the shared tests, not an Azure-specific patch.
- Full solution build: 0 warnings/errors. All 5 test projects green: Core 68, UmbracoExtensions 10, ImageFlow 19, SkiaSharp 17, **AzureBlob 7 (new)** — 121 total.

## Addendum: same storage account as originals, still separate containers (post-ticket-11 clarification)

Briefly explored, then reverted, after ticket 11 shipped `AzureBlobOriginalImageSource` alongside this cache: an initial pass made this cache default to the *same container* as originals (`ContainerName = "media"`) with a folder-style `BlobPathPrefix` to keep the two apart, requiring `ClearAsync`/`EvictExpiredAsync` to scope their blob listing to that prefix so a cache clear could never delete Umbraco's real media sharing the container.

User clarified the actual intent was narrower: same Blob Storage **account** (one `ConnectionString` usable for both), but still two separate **containers** — not one container split by folder. Reverted `AzureBlobCacheOptions.ContainerName`'s default back to `"image-derivative-cache"`, removed `BlobPathPrefix` and the prefix-scoped listing entirely (`ClearAsync`/`EvictExpiredAsync` are back to listing their whole container, which is safe again now that the container is exclusively this cache's own), and removed the two regression tests written for the shared-container scenario since it no longer applies.

Net effect, documented in `quickstart-standalone.md`'s Blob mode section: point both `AzureBlobOriginalImageSourceOptions` and `AzureBlobCacheOptions` at the same `ConnectionString` if convenient, but always give them different `ContainerName`s. AzureBlob test project back to 12 (7 original + 5 from ticket 11's original-source tests). Full solution build still 0 warnings/errors.
