# 06 — Cross-processor parity suite

**What to build:** Automated confidence that SkiaSharp and ImageFlow produce equivalent output for the same request, so switching processors is a config change, not a behavior change (ADR-0003). Build a shared parity test project/theory data running the full command set — resize, `cc` crop, format conversion, `bgcolor`, autoorient — against both processors via `IImageProcessor.Process()` (the same seam the existing 16 SkiaSharp / 19 ImageFlow unit tests already call). Assert equivalent output dimensions, output format, and pixel-similarity within a defined threshold — not byte-identical, since the two encoders legitimately differ. Use each processor's `SupportedFormats` (ticket 03) to determine which format cases apply to it, rather than a second hardcoded exclusion list.

**Blocked by:** 03 (needs `SupportedFormats` to know which formats to run per processor).

**Status:** resolved

- [x] Shared parity suite exists, driven by one set of `ParsedImageCommand` theory data reused across both processors
- [x] Covers resize, `cc` crop, format conversion, `bgcolor`, and autoorient
- [x] For each case, asserts equivalent output dimensions and output format between SkiaSharp and ImageFlow
- [x] For each case, asserts pixel similarity within a defined threshold (not byte-identical)
- [x] Format cases are scoped per processor via `SupportedFormats`, not a separately maintained exclusion list
- [x] Suite passes against the current SkiaSharp/ImageFlow implementations

## Comments

- **New project, `src/Umbraco.Image.Processing.ParityTests`**: sits directly under `src/` (not nested inside either processor's folder, matching `IntegrationTests.Shared`'s and `E2E.Tests`'s placement) since it's cross-cutting by nature — it references `Umbraco.Image.Processing.Core`, `Umbraco.Image.Processing.SkiaSharp`, and `Umbraco.Image.Processing.ImageFlow` directly, plus the `SkiaSharp` NuGet package as an independent fixture builder/decoder (the same convention `Umbraco.Image.Processing.ImageFlow.Tests` already established, and its doc comment already explains the rationale: SkiaSharp is trusted as a proven, independent decoder here, not preferred as a processor). Wired into the `.sln` as a plain root-level `Project()` entry (no solution-folder nesting), matching how `Umbraco.Image.Processing.SkiaSharp.Tests` / `.ImageFlow.Tests` are wired — verified every `GlobalSection` that needed the new GUID (`ProjectConfigurationPlatforms`; no `NestedProjects` entry needed since its siblings don't have one either) and confirmed with `dotnet sln list`.
- **`ParsedImageCommand` in the ticket text vs. the actual seam**: the ticket names `ParsedImageCommand` for the shared theory data, but `IImageProcessor.ProcessAsync` takes `ResolvedImageCommand` — the already-resolved form (pixel-space `CropRectangle`, numeric `ExifOrientation`) that Core hands processors after doing all crop/orientation math. The theory data is `ResolvedImageCommand`-shaped, matching the real seam; `ParsedImageCommand` doesn't exist as a type crossing that boundary.
- **Design: cases compare processors to each other, not to a fixed expected value.** Each theory case is a single `ResolvedImageCommand`; the test runs it through both processors and asserts *their outputs agree* (dimensions, format, pixel similarity) rather than asserting either one against a hand-computed reference image. That's the actual parity guarantee ADR-0003 asks for — "switching processors is a config change" means SkiaSharp's output and ImageFlow's output for the same command must agree with each other, not just that each independently produces *something* plausible (that's what the existing per-processor unit tests already cover).
- **Fixture: a 40x60 quadrant PNG, not the unit tests' 2x2 four-corner grid.** `ParityFixtures.QuadrantOpaquePng()` fills a 40-wide/60-tall image with four solid-colored 20x30 quadrants (red/green/blue/yellow). A 2x2 source is too small for pixel-*similarity* to mean anything — two different resample filters resizing a 2x2 source will legitimately land on different single-pixel colors with no way to tell "close" from "wrong." A large flat-quadrant image gives resize/crop comparisons a real area to average over, and the non-square, non-power-of-two dimensions (and distinct quadrant width vs. height) guard against either processor silently swapping width/height. `ParityFixtures.QuadrantTransparentPng()` is the same layout at alpha=0 everywhere, used only for the `bgcolor` case — fully transparent avoids any ambiguity about partial-alpha blend math differing between processors; a correctly-flattened result must be the solid background color everywhere regardless of what RGB sat underneath.
- **10 structural cases** (`CrossProcessorParityTests.BuildCases()`): `NoOp` (identity), `ResizeExactDistort` and two aspect-preserving resizes (width-only, height-only), `CropTopRightQuadrant` and a combined crop+resize case, three `autoorient` cases (90° rotate, 180° rotate, transpose — reusing the same `ExifOrientation` constants and expected transforms the per-processor unit tests already verified independently), and the `bgcolor` flatten case. All encode to PNG (lossless), isolating pixel disagreement to the two processors' resample filters rather than compression.
- **1 format-conversion theory**, driven by `new SkiaSharpImageProcessor().SupportedOutputFormats.Intersect(new ImageFlowImageProcessor().SupportedOutputFormats)` computed at runtime — not a hardcoded list or exclusion list. This currently resolves to `{jpg, jpeg, png, webp}` (confirmed via test output; `gif` is ImageFlow-only, `bmp` is neither's), matching what the ticket's background note already expected, but the suite derives it from the properties rather than asserting that list as ground truth, so it tracks either processor's `SupportedOutputFormats` automatically if it ever changes. A `SupportedFormatIntersection_IsNonEmpty` sanity fact guards against this theory silently running zero cases if the intersection ever became empty.
- **Pixel-similarity comparer (`PixelSimilarity.Compare`)**: decodes both outputs with SkiaSharp and computes, over every pixel, the per-channel (R/G/B/A) absolute delta. Reports three numbers: mean channel delta (0-255 scale, averaged over all pixels and channels), max channel delta, and an *outlier pixel ratio* — the fraction of pixels where the single largest channel delta exceeds a threshold (45 for PNG/structural cases, 60 for lossy-format cases). The outlier ratio exists because a single very-different pixel (e.g. one anti-aliased edge pixel) shouldn't fail a whole-image comparison the way a naive max-delta bound would, but a *broad* disagreement should. This is a real per-pixel implementation, not a placeholder — see `src/Umbraco.Image.Processing.ParityTests/PixelSimilarity.cs`.
- **Thresholds, chosen empirically, not guessed**: `StructuralMeanChannelDeltaThreshold = 10.0`, `StructuralOutlierChannelDeltaThreshold = 45`, `StructuralOutlierPixelRatioThreshold = 0.25` for the PNG/structural cases; `FormatMeanChannelDeltaThreshold = 20.0`, `FormatOutlierChannelDeltaThreshold = 60`, `FormatOutlierPixelRatioThreshold = 0.35` for the lossy-format cases. Every case's actual measured values are logged via `ITestOutputHelper` on every run (pass or fail) so the numbers stay visible, not just the pass/fail boolean. Observed real values driving these choices: most structural cases came back pixel-*identical* (mean delta 0.00 — crop, autoorient, and no-op cases have no interpolation to disagree on); resizes ranged from 1.69 to 6.91 mean delta with the outlier ratio topping out at 19.3% on the smallest resize target (10x15, `ResizeHeightOnlyAspect`) — a fixed-width edge-disagreement band naturally becomes a larger fraction of a smaller image, which is why the outlier bound is a generous 25% rather than something tighter; JPEG format-conversion came back at 2.25 mean delta / 2.7% outliers, PNG and WebP were pixel-identical. The 25%/35% outlier bounds leave real headroom above every observed value while still being a meaningful gate (not 100%/no-op).
- **Bug caught during implementation, not a design change**: `SKCodec.Create(Stream)` takes ownership of and disposes the stream it's given. The first draft of the format-conversion test called `AssertEncodedFormat` (which uses `SKCodec.Create` to read back the actual encoded format) before decoding the same stream for pixel comparison, and the second call failed with `ObjectDisposedException`. Fixed by snapshotting each processor's output to a `byte[]` once and constructing a fresh `MemoryStream` per downstream use (format check, decode) — see `CrossProcessorParityTests.SkiaSharpAndImageFlow_ProduceEquivalentOutput_ForEachCommonlySupportedFormat`.
- **Full solution build and test run**: `dotnet build` on the `.sln` — 0 warnings, 0 errors, all 19 projects (including the new one) build. Fast suites all green: Core 71, SkiaSharp 17, ImageFlow 19, UmbracoExtensions 10, AzureBlob 12, Service.Tests 9, `Umbraco.Tests` 7, and the new `ParityTests` 15 (10 structural cases + 4 format cases + 1 sanity fact). The Aspire-orchestrated `E2E.Tests` suite was left untouched, consistent with ticket 07's precedent — it boots real separate processes and isn't in scope for this ticket's checklist.
