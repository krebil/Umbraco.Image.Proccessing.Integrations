**What to build:** Every PR/branch push automatically builds the solution and runs the complete test suite — existing unit tests plus the new parity suite (06), cache-contract suite (04/05, including against Azurite), and HTTP integration tests (07) — with no publish step. This is the gate ticket 10's publish workflow will reuse.

## Comments

- **File**: `.github/workflows/build-and-test.yml`, the first workflow in this repo (no prior `.github/` directory). One job, `build-and-test`, on `ubuntu-latest`: checkout, `actions/setup-dotnet@v4` pinned to `dotnet-version: '10.0.x'` (every `.csproj` in the solution targets `net10.0`, confirmed by grepping `TargetFramework`; local SDK is 10.0.102), then a staged `dotnet restore` → `dotnet build --no-restore` → one `dotnet test --no-build` step per test project. `Directory.Build.props`'s `TreatWarningsAsErrors`/`EnforceCodeStyleInBuild` (ticket 08) mean the build step alone already fails the job on any warning; no extra warning-detection logic was added.
- **Trigger scoping**: `pull_request` (all PRs) plus `push` scoped to `main` only. A branch with an open PR against `main` doesn't also trigger the `push` event, because `push` only fires for `main` itself — so the same commit never runs the workflow twice. No other long-lived branches exist in this repo to add. Also added a `concurrency` group keyed on PR number / ref with `cancel-in-progress: true`, so a superseded commit's run gets cancelled rather than wasting runner time — small addition, standard idiom, not over-engineering.
- **Structure for ticket 10 to reuse**: kept this as a single straightforward job with named, copy-paste-consistent steps (restore → build → one test step per project) rather than building a `workflow_call` reusable-workflow abstraction. Ticket 10's publish workflow can copy the same restore/build/test step sequence verbatim into its own job ahead of its pack/push steps. Went with a plain job over `workflow_call` because ticket 10's publish workflow needs pack/push steps to run only after a full green test suite, in the same job/run — a separate reusable workflow would either need a second job (fine, but adds artifact-passing complexity for something this size) or would be reusing more machinery than the ticket calls for. Judgement call: a straightforward job is fine here.
- **Test steps kept separate per project** (not one `dotnet test` on the `.sln`): both work — ticket 08's validation ran a single `dotnet test` on the full solution successfully — but separate steps give each suite its own pass/fail status and log group in the Actions UI, which matters here because the suites have genuinely different natures (fast in-process unit tests vs. Docker-backed Azurite vs. multi-process Aspire E2E) and a failure should be attributable to the right one at a glance.
- **Cache-contract suite (AzureBlob.Tests)**: confirmed via `AzuriteFixture.cs` and `AppHost.cs` — it self-orchestrates a real Azurite container through Aspire's `DistributedApplicationTestingBuilder` (`DistributedApplicationTestingBuilder.CreateAsync<Projects.Umbraco_Image_Processing_AzureBlob_TestHost>()`), the same mechanism the product's own `Umbraco.Image.Processing.AppHost` uses. This just needs Docker reachable on the runner. No `services:` block was added — `ubuntu-latest` GitHub-hosted runners have Docker pre-installed, and the job doesn't need anything beyond that.
- **E2E.Tests — included, deliberately**: ticket 09 exists to be the complete gate ticket 10 reuses, and the ticket's "What to build" prose says "the complete test suite." `E2E.Tests` (tickets 11/12) boots the real Umbraco sample + standalone Service + Azurite as separate processes via `UmbracoServiceGraphHarness`/Aspire, with up to a 3-minute readiness timeout built into the harness itself. It's heavier than the other suites but not open-ended, so it was included as its own step, and the job's `timeout-minutes: 30` gives headroom for a slower hosted runner on top of the harness's own 3-minute internal timeout. If this turns out to be too slow or flaky in practice on GitHub-hosted runners specifically, dropping it back out to a separate, non-blocking workflow is a reasonable fallback — see "unsure" note below.
- **Local validation** (can't literally run GitHub Actions locally): validated YAML syntax with Ruby's `YAML.load_file` (Python's `yaml` module wasn't installed and pip install was blocked by the system's externally-managed-environment guard, so switched to Ruby's built-in Psych) — confirmed it parses and the job/step structure matches what was written. Note: Ruby's YAML parser strictly applies YAML 1.1 boolean coercion and reports the `on:` key as `true` rather than the string `"on"` — this is a parser quirk, not a workflow bug; every GitHub Actions workflow uses bare `on:` this way and GitHub's own workflow parser handles it correctly. Then ran every command the workflow uses, for real, locally: `dotnet --list-sdks` confirmed 10.0.102 is installed; `dotnet restore` on the `.sln`; `dotnet build -t:Rebuild --no-restore` on the `.sln` (0 warnings, 0 errors); then `dotnet test --no-build` scoped to each of the 9 test projects the workflow runs as separate steps (Core.Tests 71, SkiaSharp.Tests 17, ImageFlow.Tests 19, UmbracoExtensions.Tests 10, ParityTests 15, AzureBlob.Tests 12 with real local Docker/Azurite, Service.Tests 9, Umbraco.Tests 7, E2E.Tests 3 booting the real multi-process app graph in ~52s) — all green, 163 tests total, matching ticket 08's last-recorded baseline plus no regressions.
- **Unsure / worth a human sanity-check**: actual GitHub-hosted `ubuntu-latest` runner behavior couldn't be verified locally — specifically (1) whether Docker-in-Docker/Aspire's container orchestration behaves identically on the hosted runner's Docker daemon as it does locally (permissions, image pull time for the Azurite/Aspire dashboard images on a cold runner), and (2) whether `timeout-minutes: 30` is generous enough once real network/pull latency and a slower shared vCPU are added on top of the ~52s E2E time and ~5 total minutes seen locally. Recommend watching the first real run's timing and adjusting the timeout if needed.
