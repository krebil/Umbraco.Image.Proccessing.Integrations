# Production Hardening

Follow-on to the pluggable image-processing POC (`.scratch/pluggable-image-processing/`), which proved the abstraction but explicitly scoped out everything needed to publish it as real, public NuGet packages. See `CONTEXT.md` for vocabulary (**the product**, **reference implementation**, **UmbracoExtensions**, **cache buster**, **lockstep versioning**) and `docs/adr/0001`–`0007` for the decisions this spec builds on.

## Problem Statement

The pluggable image-processing abstraction — Core, SkiaSharp, and ImageFlow processors, in-process and standalone modes — works and is proven by manual click-through, but it isn't installable by anyone outside this repo. There are no NuGet packages, no CI, no automated guarantee that the processors stay behaviorally interchangeable, an unbounded local-disk cache, a public-license landmine sitting undisclosed in the ImageFlow processor, and a `IImageProcessor` interface that's one missing member away from a breaking change the moment it's published. An Umbraco developer who wants "a drop-in replacement for `Umbraco.Cms.Imaging.ImageSharp`, pick your processor" today has to clone this repo and build it themselves.

## Solution

Publish **the product** — four NuGet packages (`Krebil.Umbraco.Image.Processing.Core`, `.SkiaSharp`, `.ImageFlow`, `.UmbracoExtensions`) — to nuget.org, each carrying its own honest license, versioned in lockstep, released via a tag-triggered CI pipeline that only publishes when the full test suite (including a new cross-processor parity suite) is green. Split Core's Umbraco-specific interface implementations into the new `UmbracoExtensions` package so standalone consumers never inherit an Umbraco dependency they don't need. Close the two gaps that matter most before the public API locks in — processor format capability and derivative-cache growth — and leave everything else (a container image, multi-targeting, wider Umbraco-version testing) as deliberate, documented non-goals for v1.

## User Stories

1. As an Umbraco developer, I want to `dotnet add package Krebil.Umbraco.Image.Processing.Core` (plus a processor and `UmbracoExtensions`) instead of cloning this repo, so that I can adopt the abstraction the same way I adopt any other NuGet dependency.
2. As an Umbraco developer choosing between SkiaSharp and ImageFlow, I want confidence that both produce equivalent output for the same request, so that switching processors is genuinely a config change, not a behavior change.
3. As an Umbraco developer, I want the same package family naming convention as the author's other published packages (`Krebil.*`), so that I recognize it as being from the same maintainer.
4. As a maintainer, I want all four product packages to always share one version number, so that I never have to reason about which package needs a bump on a given change, or worry about a consumer running mismatched Core/processor versions.
5. As a maintainer, I want releases triggered by pushing a git tag against a version already committed to `Directory.Build.props`, so that publishing is a deliberate, auditable action rather than automatic on every merge.
6. As a maintainer, I want CI to run the full test suite — including the parity suite — before any `nuget push`, so that a regression can never reach a consumer silently.
7. As a consumer evaluating `Krebil.Umbraco.Image.Processing.Core` or `.SkiaSharp`, I want an MIT license with no encumbrance, so that I can use it in a closed-source commercial project without further review.
8. As a consumer evaluating `Krebil.Umbraco.Image.Processing.ImageFlow`, I want the AGPLv3/commercial-license obligation of the underlying `Imageflow.NET` dependency surfaced on the package's own NuGet Gallery listing, so that I see it before I install, not after.
9. As a consumer reading that same warning, I want an explicit note that third-party license terms can change and the README may be stale, so that I know to verify current terms myself rather than trust a snapshot.
10. As a standalone-only consumer (no Umbraco anywhere in my stack), I want `Krebil.Umbraco.Image.Processing.Core`/`.SkiaSharp`/`.ImageFlow` to carry zero `Umbraco.Cms.Core` dependency, so that I'm not forced to pull in an unrelated CMS assembly to process images.
11. As an in-process Umbraco developer, I want a fourth package (`Krebil.Umbraco.Image.Processing.UmbracoExtensions`) providing the `IImageUrlGenerator`/`IImageDimensionExtractor` implementations, so that in-process mode still works exactly as it does today after the split.
12. As an in-process Umbraco developer, I want the package to work across Umbraco releases without an artificial next-major version cap, so that I'm not blocked from upgrading Umbraco until this package publishes a new version for no functional reason.
13. As a maintainer, I want the Umbraco compatibility range to widen or narrow only when Umbraco actually changes media storage or the ImageSharp.Web command vocabulary, so that I'm not committing to a proactive multi-version test matrix I can't sustain alone.
14. As a library consumer calling `IImageProcessor` directly, I want to query which output formats a processor supports before requesting one, so that I can branch on capability instead of catching `NotSupportedException`.
15. As a maintainer, I want the format-capability query added before v1 ships, so that adding it later doesn't force a coordinated major-version bump across all four lockstep-versioned packages.
16. As an operator running this in production, I want the derivative cache to stop growing unboundedly, so that a long-lived deployment doesn't eventually fill its disk or storage bucket.
17. As an operator, I want cache eviction to be TTL-based using the existing `CacheControlMaxAge` setting, so that I don't have to reason about LRU/max-size tuning on top of a value I'd already configure for cache-control semantics.
18. As an operator, I want to trust that a TTL-evicted entry was never silently stale before eviction, so that eviction timing is a housekeeping detail, not a correctness concern — guaranteed by the existing `v` cache-buster query parameter already keying the cache to the source image's current version.
19. As a platform engineer wanting cloud-scale caching, I want an Azure Blob Storage implementation of `IDerivativeImageCache`, so that the standalone Service can run multiple instances behind a load balancer sharing one derivative cache.
20. As a contributor developing the Blob cache backend, I want to run and test it locally against Azurite via the Aspire AppHost, so that I don't need a real Azure subscription for day-to-day development.
21. As a contributor running CI, I want the parity and cache-contract test suites to run against Azurite in the pipeline too, so that Blob-backend regressions are caught before release, not after.
22. As an Umbraco developer relying on request-size protection, I want confirmation that `MaxWidth`/`MaxHeight` clamping already matches (and slightly exceeds) Umbraco's own `Resize` settings' DoS protection, so that I know this parity point needs no further work.
23. As an Umbraco developer relying on browser caching, I want confirmation that `BrowserCacheMaxAge` is already wired to the `Cache-Control` response header matching Umbraco's `Cache:BrowserMaxAge` semantics, so that I know this parity point needs no further work.
24. As anyone evaluating this repo on GitHub, I want a root `LICENSE` file (MIT) covering the reference implementation and repo tooling, distinct from the four packages' own licenses, so that the repo's own license status is unambiguous.
25. As anyone adapting the standalone Service or Aspire AppHost to their own deployment, I want to understand they are reference implementation — not a maintained, deployable artifact of this project (no Dockerfile, no container image) — so that I don't mistake "here's how it's done" for "here's what we host for you."
26. As a maintainer, I want the product packages to single-target `net10.0` for v1 rather than paying multi-targeting complexity up front, so that I only take on that cost if and when a real pre-net10.0 standalone consumer shows up — a change that's additive and non-breaking whenever it happens.

## Implementation Decisions

- **Package restructuring**: split the current `Umbraco.Image.Processing.Core` project so its Umbraco-specific `IImageUrlGenerator`/`IImageDimensionExtractor` implementations move to a new project/package, `UmbracoExtensions`. Core drops its `Umbraco.Cms.Core` `PackageReference` entirely. (ADR-0006)
- **Package identity**: `PackageId` = `Krebil.` + existing `AssemblyName` for all four projects (`Krebil.Umbraco.Image.Processing.Core`/`.SkiaSharp`/`.ImageFlow`/`.UmbracoExtensions`). `Service`, `Umbraco` (sample), and `AppHost` are never packed/published. (ADR-0001)
- **Versioning**: one `<Version>` in `Directory.Build.props`, shared by lockstep by all four packable projects. (ADR-0001)
- **Release pipeline**: two GitHub Actions workflows — a build+test workflow on every PR/branch push (no publish step), and a tag-triggered workflow (`v*` tags) that builds, runs the full test suite including the parity and cache-contract suites, packs all four packages, and pushes to nuget.org only on success. (ADR-0001)
- **Per-package licensing**: `PackageLicenseExpression` set individually per package — MIT for Core/SkiaSharp/UmbracoExtensions. ImageFlow's own `PackageLicenseExpression` stays MIT for the wrapper code, but its `PackageReadmeFile` (the file NuGet Gallery renders on the package's listing page) opens with the AGPLv3/commercial-license warning about the `Imageflow.NET`/`Imageflow.AllPlatforms` dependency, plus a note that license terms can change and readers must verify current terms themselves. (ADR-0002)
- **Repo license**: add a root `LICENSE` file, MIT, covering the reference implementation (`Service`, `Umbraco` sample, `AppHost`) and repo tooling — distinct from and not overridden by the per-package licenses above.
- **Umbraco dependency range**: `UmbracoExtensions`'s `Umbraco.Cms.Core` `PackageReference` uses an open floor (`>= 18.0.0`) with no upper-major cap. Core, SkiaSharp, and ImageFlow carry no Umbraco reference at all post-split. (ADR-0005)
- **`IImageProcessor` capability query**: add a member (e.g. `SupportedFormats`) exposing the set of output formats a processor actually supports, implemented for both SkiaSharp (excludes `gif`/`bmp`) and ImageFlow (excludes `bmp`) based on the encoder gaps already discovered during the POC. This is a breaking interface addition, so it must land before the v1 publish, not after. (ADR-0004)
- **Derivative cache TTL eviction**: add eviction to `IDerivativeImageCache`, driven by the existing `ImageProcessingOptions.CacheControlMaxAge` (default 365 days, currently declared but unused). Implement for both `LocalDiskDerivativeImageCache` and the new Blob implementation. No LRU/max-size logic — correctness is already guaranteed independent of eviction timing by the existing `v` cache-buster query parameter (`ImageProcessingUrlGenerator` / `options.CacheBusterValue`) changing whenever the source image does, making a stale-TTL entry provably unreferenced by any live URL. (ADR-0007)
- **Azure Blob `IDerivativeImageCache` implementation**: new implementation of the existing `IDerivativeImageCache` interface backed by Azure Blob Storage, ships in v1 (not a fast-follow) — additive against the existing seam, no interface change required.
- **Local dev/test infrastructure for Blob**: wire an Azurite resource into `Umbraco.Image.Processing.AppHost` via Aspire's `AddAzureStorage().RunAsEmulator()`, so the Blob backend is developed and tested against a real Blob-API-compatible emulator, no Azure subscription required. The same emulator is used in CI for the parity and cache-contract suites when they exercise the Blob backend.
- **No new work required**: `ImageProcessingOptions.MaxWidth`/`MaxHeight` (both already clamp independently, matching and slightly exceeding Umbraco's `Resize:MaxWidth`/`MaxHeight` DoS protection) and `BrowserCacheMaxAge` (already wired to the `Cache-Control` response header, matching Umbraco's `Cache:BrowserMaxAge`) need no changes — confirmed during this spec's grilling session, called out here so they aren't rediscovered as "gaps" later.
- **No Dockerfile/container image**: the standalone Service stays reference implementation only; no container image is built, published, or maintained by this project for it.
- **Target framework**: all four product packages single-target `net10.0` for v1.

## Testing Decisions

Tests should assert observable behavior through the interfaces below, not internal implementation — a test that would need to change if the internal algorithm changed without changing the interface's contract is testing the wrong thing.

- **`IImageProcessor` parity suite** (new, shared test project or shared theory data referenced by both processors' existing test suites): the same set of `ParsedImageCommand`s (covering resize, `cc` crop, format conversion, `bgcolor`, autoorient) run against both SkiaSharp and ImageFlow, asserting equivalent output dimensions, output format, and pixel-similarity within a defined threshold — not byte-identical, since the two encoders legitimately differ. Prior art: the existing per-processor unit tests (16 SkiaSharp, 19 ImageFlow) already call `IImageProcessor.Process()` directly at this seam; the parity suite reuses it rather than introducing a new one.
- **`IImageProcessor.SupportedFormats` tests**: assert each processor's declared `SupportedFormats` set is exactly consistent with what it accepts vs. throws `NotSupportedException` on — no format is claimed as supported that actually throws, and no format that succeeds is left off the declared set.
- **`IDerivativeImageCache` contract suite** (new, shared): one suite of tests against the `IDerivativeImageCache` interface — read/write/clear round-trip, and the new TTL-eviction behavior (an entry older than `CacheControlMaxAge` is no longer returned by `TryOpenReadAsync` and is removed on the next eviction pass) — run parameterized against both `LocalDiskDerivativeImageCache` and the new Blob implementation (the latter against Azurite in CI). One shared suite, not bespoke tests per backend, mirroring the parity suite's shared-across-implementations pattern.
- **HTTP-level integration tests** (new, standard ASP.NET `WebApplicationFactory`, not a new seam this project invents): cover the Service's and in-process sample's middleware pipeline wiring — pass-through, resize, format conversion, `cc` crop, and HMAC-signed request accept/tampered-or-unsigned reject, at the status-code/header/content-type level. Pixel correctness is not re-asserted here — that's the parity suite's job at the lower seam; these tests exist to catch wiring/registration regressions (e.g. middleware mounted in the wrong order, DI misregistration) that unit tests at the processor/cache seam can't see.
- **CI gate**: the tag-triggered publish workflow must run all of the above (existing unit tests + new parity suite + new cache-contract suite + new integration tests) and only proceed to `nuget push` on full green.

## Out of Scope

- **Container image / Dockerfile** for the standalone Service — explicitly reference implementation, not a maintained deployable, for v1 and for the foreseeable future (this project's product is the NuGet packages, not a hosted service).
- **Multi-targeting below `net10.0`** — deferred until a real standalone consumer needs it; adding a TFM later is additive and non-breaking.
- **Proactive multi-major Umbraco version testing** — the compatibility range stays open by design (ADR-0005); this project doesn't commit to testing against every Umbraco major as it ships, only reactively when media storage or the command surface actually changes.
- **A third processor** beyond SkiaSharp and ImageFlow.
- **Observability/telemetry beyond existing `ILogger` usage in the middleware** — not raised as a gap during this spec's grilling session; revisit only if real operational usage surfaces a need.
- **Secret management/rotation tooling** (e.g. Key Vault integration) for the HMAC signing key — the reference implementation demonstrates configuring a shared secret; production secret management is the adopting operator's responsibility, consistent with the reference-implementation framing.
- **Rate limiting** on the standalone Service — reference implementation, not a hardened deployable; an operator adapting it for production is expected to add their own.
- **Cache folder nesting-depth/hash-length tuning** to match Umbraco's exact `CacheFolderDepth`/`CacheHashLength` defaults — the existing SHA-256-based nesting in `LocalDiskDerivativeImageCache` is a working, if differently-tuned, equivalent; not treated as a gap.
