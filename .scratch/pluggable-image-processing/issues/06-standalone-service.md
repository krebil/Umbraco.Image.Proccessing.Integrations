## Question

Create `src/Umbraco.Image.Processing.Service` — a plain ASP.NET Core project (no Umbraco reference, mirroring the standalone service described in `imagesharp-standalone-service-plan.md`) that hosts Core's middleware directly:

- Reference Core and (at minimum) the SkiaSharp processor project; register the pipeline the same way the in-process sample does, just as the entire app rather than mounted alongside Umbraco.

- Confirm HMAC-signed requests generated by the `Umbraco` sample's URL generator are correctly validated when served by this separate process.
- Once the ImageFlow processor ticket lands, confirm this service also works with `.UseImageFlow()` selected.

**Also in scope — direct URL generation, alongside the redirect (decided 2026-08-20, supersedes the map's original "documentation only" note):**

- Add an optional external-base-URL setting to Core's `ImageProcessingOptions` (e.g. `ExternalBaseUrl`). When set, `ImageProcessingUrlGenerator` prefixes its generated URLs with it, producing an absolute URL that points straight at this standalone service instead of a relative `/media/...` URL.
- The `Umbraco` sample project sets this when `ImageProcessing:Mode = Standalone`, so freshly-rendered pages link directly to the standalone service — no redirect round-trip for the common case.
- The redirect middleware built in the In-Process Sample ticket (05) stays in place regardless — it's the fallback for any `/media` request that reaches the Umbraco app without the host already baked in (rich-text-embedded image URLs, hand-typed/bookmarked URLs, anything from before the config was turned on).
- Confirm both paths work: a freshly-generated `<img>` URL goes straight to this service, and a bare relative `/media/...` URL hitting the `Umbraco` sample gets redirected here correctly.
