Type: wayfinder:map

## Destination

A working proof-of-concept for a pluggable Umbraco image-processing abstraction. A shared Core project defines the processor abstraction, models, and shared concerns (command parsing/normalization, HMAC signing) independent of any specific imaging library. Two processor projects — SkiaSharp and ImageFlow — implement that abstraction as drop-in replacements for `Umbraco.Cms.Imaging.ImageSharp`, each supporting the full ImageSharp.Web stock query-string command surface (`width`, `height`, `format`, `quality`, `bgcolor`, autoorient) plus Umbraco's `cc` crop/focal-point command, with HMAC signing working identically across all three. Each processor must be runnable both **in-process** (same app service as Umbraco) and as a **separate standalone deployment**, with an individual quickstart `.md` guide per mode, written so they can be linked directly from blog posts or the README.

Proven by manual click-through: the Aspire AppHost boots, the sample site renders resized/cropped images correctly under each processor config, the `cc` crop command produces the correct crop, and HMAC-signed URLs are accepted/rejected correctly. No automated parity suite required for the POC.

## Notes

- **This map carries execution.** Tickets are build tasks resolved by implementing them directly, not pure decisions — an intentional override of wayfinder's default (see the map skill's "Plan, don't do" section). Still: never resolve more than one ticket per session, research tickets excepted.
- Prior art: `imagesharp-standalone-service-plan.md` at the repo root — the standalone-deployment redirect/CDN pattern it describes carries over, made processor-agnostic.
- Repo already pins Umbraco.Cms 18.1.1 (`src/Umbraco/Directory.Packages.props`) and targets net10.0 across projects.
- Existing projects: `src/Umbraco` (sample site, currently unconfigured for imaging) and `src/Umbraco.Image.Processing.Core` (empty scaffold).
- Standing preferences locked during grilling:
  - Storage backend for the POC is **local disk only**. Azure Blob support is real future work but out of scope here (see below).
  - Core owns the middleware, canonical command parsing/normalization/validation, and HMAC signing. Each processor project implements only `IImageProcessor` (decode → transform → encode).
  - Core owns **one single** `IImageUrlGenerator` + dimension-extractor implementation, shared by all three processors (output format never varies by processor, so no per-processor variant is needed).
  - **Revised 2026-08-20** (was: "Standalone mode needs no URL-generation code — documentation only"): Standalone mode gets **both** the redirect middleware (already built in the In-Process Sample ticket) **and** real URL generation. Core's `ImageProcessingUrlGenerator` gains an optional external-base-URL so it can emit absolute URLs pointing straight at the standalone host, skipping the redirect round-trip for the common case. The redirect stays as a fallback for URLs that weren't generated with the host baked in (rich-text-embedded image URLs, hand-typed URLs, anything hitting the Umbraco app's `/media` directly). No separate `IMediaUrlProvider`/CDN-provider hook — that's a lower-level abstraction (resolves a media item's base path, not the crop/resize querystring URL) and doesn't exist as `AddCdnMediaUrlProvider` in Umbraco.Cms 18.1.1 regardless.
  - Quickstart docs: **two total** (in-process, standalone), each generic across processors via a config swap — not six.
  - `.NET Aspire` (`Umbraco.Image.Processing.AppHost`) orchestrates local dev/demo only — wires up the sample site, the standalone service, and later storage emulators. The quickstart docs stay Aspire-free.
  - In-process vs standalone switch in the sample `Umbraco` project is a config value (e.g. `ImageProcessing:Mode = InProcess | Standalone`).
  - ImageFlow's integration mechanism (`Imageflow.NET` direct vs. anything from `Imageflow.Server`) is left to agent discretion — resolve via the research ticket, prioritizing drop-in query-string parity over reusing existing middleware.
  - **Imageflow licensing**: actually executing a job via `Imageflow.NET` (`InProcessAsync()`) requires AGPLv3 compliance or a commercial imazen license — independent of using `Imageflow.Server` or not. Flag this plainly in the quickstart docs (tickets 08/09).
- Relevant skills: `/tdd` for the Core/processor build tickets if red-green fits naturally; `/research` for the ImageFlow ticket.

## Decisions so far

- [ImageFlow Integration Research](issues/01-imageflow-integration-research.md) — Call `Imageflow.NET`'s in-process fluent job API (`ImageJob`/`BuildNode` → `InProcessAsync()`) directly from `IImageProcessor.Process()`, bypassing `Imageflow.Server` entirely. Core computes the `cc` crop pixel-rectangle and EXIF-orientation rotation (ported from Umbraco's own `CropWebProcessor` math) since Imageflow has no focal-point or autoorient node. Single package `Imageflow.AllPlatforms`; native runtimes still RC-versioned. Full detail: [`research/imageflow-integration.md`](research/imageflow-integration.md).
- [Core Abstraction](issues/02-core-abstraction.md) — Built `src/Umbraco.Image.Processing.Core`: canonical command model, `IImageProcessor` seam, HMAC signing, the shared `IImageUrlGenerator`/`IImageDimensionExtractor` (implementing Umbraco's own interfaces directly), local-disk storage, and `AddImageProcessing()` DI surface. Core resolves the crop rectangle and EXIF orientation itself — via a small from-scratch header/EXIF reader, no imaging-library dependency — so processors only decode/transform/encode. 64 unit tests, solution builds clean.
- [SkiaSharp Processor](issues/03-skiasharp-processor.md) — Built `src/Umbraco.Image.Processing.SkiaSharp`: decode → crop → orientation-correct (exact per-pixel matrices derived from Core's own `ExifOrientationTransform`) → resize → background-flatten → encode, plus `UseSkiaSharp()` DI registration. SkiaSharp's native encoder only supports `jpg`/`jpeg`/`png`/`webp` — `gif`/`bmp` requests throw `NotSupportedException`, a real gap the sample/quickstart tickets (05/06/08/09) need to account for. 16 unit tests, solution builds clean.
- [ImageFlow Processor](issues/04-imageflow-processor.md) — Built `src/Umbraco.Image.Processing.ImageFlow`: calls Imageflow.NET's in-process fluent job API directly (`ImageJob`/`BuildNode` → `InProcessAsync()`), never `Imageflow.Server`, per the research ticket. Crop/resize/autoorient/bgcolor/format all implemented against Imageflow's node vocabulary; two behaviors (`Rotate90`/`Rotate270` direction, and using a same-size pad-mode `Constrain` to flatten transparency since no dedicated flatten node exists) were undocumented and verified empirically via passing pixel-exact tests, not derived from docs alone. Unlike SkiaSharp, ImageFlow **does** support `gif` output; like SkiaSharp, neither supports `bmp`. 19 unit tests, solution builds clean.
- [In-Process Sample](issues/05-in-process-sample.md) — Wired `src/Umbraco` to Core + SkiaSharp + ImageFlow behind a config-driven `ImageProcessing:Mode` (`InProcess`/`Standalone`) and `ImageProcessing:Processor` (`SkiaSharp`/`ImageFlow`) switch — processor is a config value, not a code edit, so the quickstart docs can do a config-only swap. `InProcess` mounts Core's middleware ahead of Umbraco's own pipeline; `Standalone` wires a processor-agnostic port of the plan doc's redirect middleware (no standalone service to redirect to yet — that's ticket 06). Manually verified via `curl` against both processors: pass-through, resize, format conversion, and `cc` crop all correct; derivative cache populates. Also fixed the sample's CMS boot failure — the unattended-install config used stale (pre-18.x) property names; corrected to `InstallUnattended`/`UnattendedUserName`/`UnattendedUserEmail`/`UnattendedUserPassword` per Umbraco.Cms 18.1.1's actual schema, and the site now installs and boots cleanly (`/` and `/umbraco` both 200). No authored content/templates yet — that's still ticket 10's job.
- [Standalone Service](issues/06-standalone-service.md) — Built `src/Umbraco.Image.Processing.Service`: a bare ASP.NET Core project (Core + SkiaSharp + ImageFlow only, no Umbraco reference) whose whole pipeline is `AddImageProcessing().Use<Processor>()` + `app.UseImageProcessing()`, reading originals straight out of the `Umbraco` sample's own `wwwroot/media` folder. Also added `ImageProcessingOptions.ExternalBaseUrl` to Core — when set, `ImageProcessingUrlGenerator` prefixes generated URLs with it, so `Umbraco`'s `Standalone` mode now emits absolute URLs pointing straight at this service (falls back to `Standalone:BaseUrl`) alongside the redirect middleware, which stays as the fallback path. Added the missing `ImageProcessing:HmacSecretKey` to both apps' `appsettings.json` (previously unset, signing silently disabled) so the two processes actually share a signing secret. Manually verified: signed requests (passthrough/resize/crop/gif) succeed against the service, tampered/unsigned ones 400; processor swap (`ImageFlow`↔`SkiaSharp`) is config-only on the service too; the sample's redirect fires correctly for bare `/media/...` URLs. 67/67 Core unit tests pass (6 new, covering `ExternalBaseUrl`). Freshly-generated `<img>` URLs pointing straight at the service are verified by code path + unit test only — no authored content yet to click through (ticket 10's job).
- [Aspire AppHost](issues/07-aspire-apphost.md) — Built `src/Umbraco.Image.Processing.AppHost` (Aspire 13.5.0, `net10.0`, no workload needed) wiring `Umbraco` and `Umbraco.Image.Processing.Service` into one app graph; `WithEnvironment` feeds the service's DCP-assigned endpoint into `ImageProcessing:Standalone:BaseUrl` so the redirect/URL target tracks the real port rather than a hardcoded one. Only `AddProject` calls so far — an emulator resource (e.g. Azurite) is a pure addition later, no restructuring needed. `dotnet run` on the AppHost verified to boot both processes cleanly (DCP requires *some* container runtime present even with zero containers declared — Docker Desktop was already installed here). AppHost isn't referenced by, or referenced from, either quickstart doc. Flagged a pre-existing, unrelated `.sln` conflict from a concurrent session's in-flight work (duplicate `Umbraco.Image.Processing.Service` name) — not fixed here, belongs to that session.
- [In-Process Quickstart](issues/08-in-process-quickstart.md) — Wrote [`docs/quickstart-in-process.md`](../../docs/quickstart-in-process.md), grounded in the in-process sample's actual `Program.cs`/`appsettings.json` and Core's DI surface: registration order (after `CreateUmbracoBuilder()`), the `.UseSkiaSharp()`/`.UseImageFlow()` swap, middleware mount point, full options table, and a three-way comparison against stock `AddUmbracoImageSharp()`. One flagged deviation from the ticket's wording: since the processor projects aren't published to NuGet, "adding the package" is `dotnet add reference`, not `dotnet add package` — called out explicitly in the doc rather than glossed over. Carries the SkiaSharp format gap, HMAC config note, and ImageFlow licensing note forward from earlier tickets. Not yet walked end-to-end as a reader — that's Manual Verification's job.
- [Standalone Quickstart](issues/09-standalone-quickstart.md) — Wrote [`docs/quickstart-standalone.md`](../../docs/quickstart-standalone.md), cross-linked with the in-process doc and grounded in the actual `Umbraco.Image.Processing.Service` sample. Documents the redirect + `ExternalBaseUrl` split (freshly generated URLs skip the redirect; everything else falls back to it) as doc-only, per the map's standing decision that URL generation never varies by processor or mode. Same `dotnet add reference` caveat, HMAC secret-sharing steps, processor-swap story, and ImageFlow licensing note as the in-process doc. Both quickstart tickets are now resolved, so Manual Verification is unblocked.
